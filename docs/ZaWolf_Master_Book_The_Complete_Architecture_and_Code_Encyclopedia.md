# الباب الأول: الرؤية، الهوية، والقواعد المعمارية الثابتة

## 1.1 ما هو نظام ZaWolf؟ وفلسفة المعالجة المحلية (Local-First On-Premise)
نظام **ZaWolf** هو حل برمجي متكامل ومحلي بالكامل تم تصميمه لمعالجة وتحويل الوثائق الطبية غير المتجانسة (مثل: الروشتات الورقية المكتوبة بخط اليد، تقارير التحاليل الرقمية، تقارير الأشعة الممسوحة ضوئياً، ملفات الوورد الطبية، وسجلات المرضى المجدولة في Excel و CSV) إلى بيانات علائقية مهيكلة داخل قاعدة بيانات Microsoft SQL Server (`ZaWolfDB`).

### المبادئ الفلسفية التي بُني عليها النظام:
1. **السيادة والخصوصية المطلقة للبيانات الطبية (Medical Privacy & Compliance):** المستشفيات والعيادات لا يمكنها قانونياً أو أخلاقياً إرسال ملفات المرضى أو أسماء الأدوية إلى واجهات سحابية تجارية خارجية (Cloud APIs). لذلك، فإن ZaWolf يعمل 100% محلياً (On-Premise / Air-Gapped) بدون الحاجة لأي اتصال إنترنت؛ حيث تُدار نماذج الرؤية (OCR) ونماذج اللغة (LLM via Ollama) وقاعدة البيانات على خوادم المنشأة ذاتها.
2. **المسار الموحد (Unified Ingestion Gateway):** لا يُطلب من المستخدم أو الطبيب أو الموظف تحديد كيف سيعالج الملف؛ يكتفي المستخدم برفع الملف، ويتولى النظام كشف النوع وتوجيهه للمعالج المناسب واستخراج بياناته وحفظها في الجداول المخصصة تلقائياً.

## 1.2 القواعد الهندسية والمعمارية الـ 22 الصارمة (System Invariants)
هذه القواعد بمثابة "دستور معماري" لا يجوز لأي مطور أو نموذج ذكاء اصطناعي التعديل عليها أو مخالفتها:

1. **كشف نوع الملف مبني على القواعد:** يتم تحديد نوع الملف بناءً على امتداد الملف الفعلي وليس بالتخمين.
2. **التوجيه حتمي (Deterministic Routing):** يقرر موجه المسارات (`router.py`) مسار المعالجة المناسب لكل ملف بشكل قاطع.
3. **تحويل PDF الممسوح ضوئياً إلى صور:** صفحات الـ PDF الممسوحة ضوئياً (Scanned) تتحول فوراً إلى صور وتدخل مسار الصور نفسه.
4. **لا توجد معمارية OCR منفصلة للـ Scanned PDF:** نفس مسار الصور والـ OCR الموحد هو المسؤول عن قراءة صفحات الـ PDF الممسوحة.
5. **معالجة مسبقة عامة للصور:** تخضع الصور لضبط الاتجاه EXIF، التدرج الرمادي Grayscale، وضبط التباين Autocontrast قبل الـ OCR.
6. **ملفات Excel و CSV لا تمر على OCR نهائياً:** تستخرج بياناتها رقمياً وبشكل مباشر عبر مكتبة Pandas.
7. **ملفات Word لا تمر على OCR نهائياً:** تستخرج نصوصها وجداولها مباشرة عبر DOM الخاص بـ python-docx.
8. **ملفات PDF الرقمية تستخرج كنصوص مباشرة:** يتم استخراج نصوصها عبر PyMuPDF دون أي حاجة للـ OCR.
9. **وظيفة الـ OCR هي تحويل الصورة لنص خام فقط:** محرك الـ OCR لا يحلل ولا ينظم ولا يستنتج؛ دوره فقط قراءة الحروف من الصورة.
10. **النموذج اللغوي (LLM) مشترك بعد الاستخراج:** كل النصوص الخام (سواء من PDF، Word، أو صور الـ OCR) تتجمع وتدخل نفس محرك الـ LLM.
11. **الـ LLM ينظم ويوحد ولا يخترع:** دور الـ LLM هو تنظيف وتوحيد وتعيين الحقول، وممنوع عليه منعاً باتاً اختراع أي معلومة طبية ناقصة.
12. **الحفاظ على القيم المفقودة (Missing Values Preserved):** أي قيمة غير موجودة في المستند الأصلي تُترك `null` أو فارغة ولا يتم افتراضها.
13. **عدم تنظيف أو فلترة ملفات Excel/CSV أثناء الاستخراج:** تبقى البيانات الخام كما هي في مرحلة الاستخراج الأولية.
14. **لا تحليل لجودة البيانات أثناء الاستخراج المبدئي:** الاستخراج يركز على سلامة القراءة فقط.
15. **التحقق (Validation) يتم بعد معالجة الـ LLM:** لا يتم إدخال البيانات لقاعدة البيانات إلا بعد اجتياز فحص Pydantic.
16. **البيانات غير الصالحة تُحول للمراجعة البشرية:** أي مستند يفشل في التحقق يُرفض بوسم `invalid` ولا يُسرب لقاعدة البيانات.
17. **قاعدة البيانات هي طبقة التخزين النهائية فقط:** لا يتم إنشاء أي معالجات ذكاء اصطناعي داخل قاعدة البيانات.
18. **النمطية التامة (Modular System):** كل طبقة منفصلة تماماً عن الأخرى ويمكن استبدال محركاتها بسهولة.
19. **عزل الروشتات الطبية (Prescription Entity Isolation):** إذا كشف حارس الاستخراج أن الملف روشتة علاجية، يتم فوراً تصفير كافة الجداول غير المتعلقة بالأدوية لمنع الهلوسة.
20. **المعاملات الذرية لقاعدة البيانات (Single Transaction Atomicity):** كل عملية حفظ مستند تتم في اتصال واحد، مؤشر واحد (Cursor)، ومعاملة ذرية واحدة تدعم التراجع التام (`Rollback`).
21. **تخريج المفاتيح الأجنبية يتم في طبقة قاعدة البيانات:** النموذج اللغوي لا يصنع IDs؛ بل تقوم فئة `RelationResolver` بالبحث في قاعدة البيانات وربط المعرفات التلقائية.
22. **عدم إضافة ميزات معقدة قبل استقرار المرحلة الحالية:** التركيز دائماً على استقرار واعتمادية خط الإنتاج الحالي.

# الباب الثالث: طبقة الاستقبال والتوجيه (Ingestion & Routing Subsystem)

## 3.1 فحص وتحديد نوع الملفات (`src/ingestion/file_detector.py`)
هذا الملف هو نقطة الاتصال الفيزيائية الأولى بأي مستند على القرص الصلب.

* **الدالة `get_input_files()`:**
  * تقوم بمسح مجلد `INPUT_DIR` وتجميع كافة المسارات الصالحة للملفات الموجودة بداخله.
* **الدالة `detect_file_type(file_path)`:**
  * **المدخل:** مسار الملف `file_path` (ككائن `Path` أو نص `str`).
  * **آلية العمل:**
    1. تتحقق أولاً من وجود الملف عبر `if not file_path.exists():` وتثير خطأ `FileNotFoundError` إذا لم يوجد.
    2. تستخرج الامتداد وتحوله لحروف صغيرة عبر `file_path.suffix.lower()`.
    3. تقارن الامتداد بجدول الامتدادات المعتمدة في `SUPPORTED_EXTENSIONS`.
  * **المخرج:** قاموس قياسي يحتوي على:
    ```python
    {
        "file_name": file_path.name,
        "file_path": str(file_path),
        "extension": extension,
        "file_type": file_type or "unsupported",
        "supported": file_type is not None
    }
    ```

## 3.2 موجه المسارات الميكانيكي (`src/ingestion/router.py`)
المسؤول عن توجيه المستند للمسار المتخصص بناءً على `file_type`.

* **الدالة `route_file(file_info)`:**
  * تقرأ نوع الملف وتحدد اسم خط الأنابيب:
    * `"pdf"` ──► `"pdf_pipeline"`
    * `"image"` ──► `"image_pipeline"`
    * `"excel"` ──► `"excel_pipeline"`
    * `"csv"` ──► `"csv_pipeline"`
    * `"word"` ──► `"word_pipeline"`
    * أي نوع غير مدعوم ──► `"unsupported"`

## 3.3 إعدادات النظام وثوابت البيئة (`config/settings.py`)
يضبط المسارات والحدود التشغيلية الحاكمة:
* `PROJECT_ROOT`: المسار الجذري التلقائي `Path(__file__).resolve().parent.parent`.
* `DATA_DIR`, `INPUT_DIR`, `PROCESSED_DIR`, `OUTPUT_DIR`: مسارات مجلدات البيانات.
* `IMAGE_PROCESSED_DIR`: مجلد حفظ الصور بعد المعالجة المبدئية (`data/processed/images`).
* `PDF_IMAGES_DIR`: مجلد حفظ صفحات الـ PDF الممسوحة ضوئياً بعد تحويلها لصور (`data/processed/pdf_images`).
* `MAX_BATCH_TEXT_SIZE = 12000`: الحد الأقصى لطول الدفعة النصية (12 ألف حرف) لمنع اختناق النماذج اللغوية.
* `BATCH_MEMORY_SAFETY_RATIO = 0.25`: نسبة أمان الذاكرة؛ يمنع استخدام أكثر من 25% من الذاكرة الشاغرة في دفعة واحدة.
* `SUPPORTED_IMAGE_EXTENSIONS`: الامتدادات المدعومة للصور: `.jpg`, `.jpeg`, `.png`, `.webp`.
* `SUPPORTED_EXTENSIONS`: خريطة مطابقة الامتدادات بالأنواع الأساسية.

# الباب الرابع: معالجات المستندات المتخصصة (Processors Deep Dive)

## 4.1 معالج ملفات PDF الرقمية والممسوحة ضوئياً (`src/processors/pdf_processor.py`)
يستخدم مكتبة `pymupdf` (المعروفة بـ `fitz`) لتحليل ملفات PDF والتمييز بين النوع الرقمي والممسوح ضوئياً:

* **`detect_pdf_type(file_path)`:**
  * يفتح الملف عبر `fitz.open(file_path)`.
  * يمر على كل صفحة ويجمع أطوال النصوص عبر `len(page.get_text("text").strip())`.
  * إذا كان مجموع أطوال النصوص أكبر من الصفر يُصنف المستند كـ `"digital"`، وإذا كان صفراً يُصنف كـ `"scanned"`.
* **`extract_pdf_pages(file_path)`:**
  * مخصص للـ PDF الرقمي؛ يقوم باستخراج النصوص مجمعة في دفعات (Batches) تراعي سقف الـ 12,000 حرف وميزانية الذاكرة الحية للجهاز.
* **`create_contextual_chunks(page_batch, file_name)`:**
  * يدمج نصوص الدفعة ويقسمها لأجزاء سياقية باستخدام `RecursiveCharacterTextSplitter` بحجم قطعة 1500 حرف وتداخل 300 حرف لضمان عدم انقطاع سياق الجمل الطبية.
* **`convert_pdf_to_images(file_path, output_dir)`:**
  * مخصص للـ PDF الممسوح ضوئياً؛ يقوم بتحويل كل صفحة إلى صورة PNG عبر استخراج مصفوفة البكسل `page.get_pixmap(matrix=fitz.Matrix(1, 1), alpha=False)` وحفظها في مجلد `PDF_IMAGES_DIR` بصيغة `{file_stem}_page_{page_number}.png`.

## 4.2 معالج الصور وتحسين التباين والرؤية (`src/processors/image_processor.py`)
مسؤول عن فحص وتأهيل الصور قبل دخولها نماذج التعرف الضوئي (OCR):
* **`load_and_validate_image(file_path)`:**
  * يتحقق من الامتداد، ويفتح الصورة عبر Pillow `Image.open()`.
  * يستدعي `image.load()` للتأكد من عدم تلف الصورة (Corruption Check).
* **`preprocess_image(file_path, output_path)`:**
  * يصحح اتجاه الصورة المائل الناتج عن كاميرات الهواتف الذكية عبر `ImageOps.exif_transpose(image)`.
  * يحول الصورة إلى التدرج الرمادي `image.convert("L")` لتسهيل قراءة الحروف وتخفيف حجم المعالجة.
  * يطبق تحسين التباين التلقائي `ImageOps.autocontrast(image)` لإبراز النصوص الباهتة.
  * يحفظ الصورة المعالجة في مجلد `IMAGE_PROCESSED_DIR` بصيغة `{file_stem}_processed.png`.

## 4.3 معالج مستندات Word والفقرات والجداول (`src/processors/word_processor.py`)
يتعامل مع مستندات `.docx` عبر مكتبة `python-docx`:
* **`extract_word_content(file_path)`:**
  * يستخرج نصوص الفقرات المكتوبة ويمنحها معرف `source_type="paragraph"`.
  * يستخرج محتويات الجداول ويحول الصفوف إلى نصوص مفصولة بفواصل ` | ` ويمنحها معرف `source_type="table"`.
* **`process_word(file_path)`:**
  * يمرر الوحدات النصية لدوال التقطيع وإدارة الذاكرة عبر `process_text_units`.

## 4.4 معالج البيانات المنظمة Excel و CSV (`src/processors/structured_processor.py`)
* **`extract_structured_data(file_info)`:**
  * لملفات CSV: يقرأ الملف عبر `pd.read_csv(file_path)`.
  * لملفات Excel: يقرأ كافة أوراق العمل (Sheets) عبر `pd.read_excel(file_path, sheet_name=None)`.
  * يعيد كائناً يحتوي على قواميس الـ DataFrames الخام دون أي تعديل أو تنظيف مبكر لضمان أمان البيانات.

## 4.5 أدوات الذاكرة والتقطيع النصي (`src/utils.py`)
* **`get_dynamic_batch_limit()`:** يستعلم عن الذاكرة العشوائية المتاحة في النظام عبر `psutil.virtual_memory().available` ويحدد ميزانية الأمان بنسبة 25%.
* **`batch_text_units(text_units)`:** يجمع الوحدات النصية في دفعات تراعي حدي الحجم النصي والذاكرة الشاغرة.
* **`create_text_chunks(text_batch, file_name)`:** يقسم النصوص الطويلة إلى Chunks بحجم 1500 حرف وتداخل 300 حرف.

# الباب الخامس: منظومة التعرف الضوئي على الحروف والرؤية الحاسوبية (OCR Subsystem)

## 5.1 كاشف العتاد وتسريع كارت الشاشة (`src/ocr/device.py`)
* **`get_device(preference="auto")`:**
  * يفحص توفر كارت شاشة Nvidia يدعم CUDA عبر `torch.cuda.is_available()`.
  * إذا كان التفضيل `"auto"` يعيد `"cuda"` في حال توفره، وإلا يعيد `"cpu"`.
  * إذا طُلب `"cuda"` ولم يكن متاحاً يطلق استثناء `RuntimeError`.

## 5.2 محرك النصوص المطبوعة PaddleOCR (`src/ocr/ocr_engine.py`)
* فئة **`OCREngine(lang="ar")`**:
  * تضبط متغير البيئة `FLAGS_enable_pir_api = "0"` لتفادي مشاكل التوافقية.
  * تنشئ محرك `PaddleOCR(lang=lang, enable_mkldnn=False)` المخصص لقراءة التقارير والمستندات الطبية المطبوعة باللغتين العربية والإنجليزية.
  * تستدعي `engine.predict()` وتمرر النتيجة لـ `parse_paddle_result` لاستخراج النصوص ومعدل الثقة (Confidence).

## 5.3 محرك خط اليد المتقدم للروشتات Qwen2.5-VL-3B (`src/ocr/handwriting_ocr.py`)
المحرك الأكثر تطوراً في المنظومة، مبني على أحدث نماذج الرؤية واللغة (Vision-Language Models):
* **النموذج المستخدم:** `sherif1313/Arabic-handwritten-OCR-4bit-Qwen2.5-VL-3B-v3`.
* **المكتبات:** `transformers` (`AutoProcessor` و `Qwen2_5_VLForConditionalGeneration`).
* **البرومبت الموجه للنموذج:**
  ```text
  Transcribe all handwritten text in this image exactly as it appears. 
  Preserve medicine names, numbers, dosages, units, and instructions. 
  Do not add information that is not visible.
  ```
* **آلية المعالجة:**
  * يفتح الصورة ويحولها لنظام ألوان RGB.
  * يطبق قالب الدردشة Chat Template ويحول الصورة والنص إلى Tensors.
  * ينفذ الاستنتاج تحت وضع `torch.inference_mode()` مع سقف توليد `max_new_tokens=512`.
  * يفك ترميز الحروف المولدة ويستخرج أسماء الأدوية والجرعات بخط اليد بدقة استثنائية.

## 5.4 الموجه الذكي لمحركات الـ OCR (`src/ocr/ocr_router.py`)
* فئة **`OCRRouter`**:
  * تعتمد على نمط **التحميل الكسول (Lazy Loading)**؛ فلا يتم تحميل نموذج Qwen الضخم أو PaddleOCR في ذاكرة كارت الشاشة إلا عند الحاجة الفعلية لتوفير موارد الجهاز.
  * الدالة `process(image_path, engine="qwen")`: توجه الصورة إلى محرك خط اليد Qwen إذا حُدد `"qwen"`، أو إلى PaddleOCR إذا حُدد `"paddle"`.

# الباب السادس: محرك الاستنتاج الذكي والذكاء الاصطناعي (LLM Engine)

## 6.1 عميل خادم Ollama المحلي (`src/llm/local_llm.py`)
يتولى الاتصال بخادم Ollama المحلي العامل على منفذ `http://localhost:11434`:
* يستدعي نقطة النهاية `/api/generate`.
* يرسل معايير صارمة:
  * `"model": "qwen3:latest"` (أو أي نموذج محلي يحدده المستخدم).
  * `"format": "json"`: لإجبار الموديل على إخراج JSON صالح برمجياً بنسبة 100%.
  * `"stream": False`: لانتظار الرد كاملاً.
  * `"think": False`: لإلغاء التفكير المطول والحصول على النتيجة المهيكلة مباشرة.
  * مهلة الاتصال `timeout = 600` ثانية للسماح بمعالجة النصوص الطويلة دون انقطاع.

## 6.2 مخططات الكيانات الطبية الـ 19 Pydantic (`src/llm/llm_schema.py`)
يحدد بدقة متناهية الحقول وأنواع البيانات للـ 19 كياناً طبياً:
1. `LocationData`: الفروع (الاسم، العنوان، الهاتف).
2. `StaffData`: الطاقم الطبي (الاسم الكامل، الدور، رقم الترخيص، الفرع، النشاط).
3. `ClientData`: المرضى (الاسم الأول والأخير، تاريخ الميلاد، النوع، الهاتف، الإيميل، العنوان، التنبيهات الطبية).
4. `MedicalHistoryData`: التاريخ المرضي (النوع، الاسم، الملاحظات، تاريخ التسجيل).
5. `VitalData`: العلامات الحيوية (ضغط الدم، النبض، الحرارة، الوزن، التاريخ).
6. `LabResultData`: نتائج المختبر (اسم الفحص، القيمة المقاسة، الوحدة، المعدل المرجعي، التاريخ).
7. `MedicationData`: الأدوية (اسم الدواء، الجرعة، التكرار، تاريخ البدء والانتهاء).
8. `ServiceData`: الخدمات والعمليات (الاسم، التصنيف، المدة بالدقائق، السعر).
9. `AppointmentData`: المواعيد (اسم المريض، الطبيب، الفرع، الخدمة، الغرفة، البداية والنهاية، الحالة، الملاحظات).
10. `TreatmentRecordData`: سجلات الجلسات (رقم الموعد، اسم المنتج، الوحدات المستخدمة، رقم التشغيلة، الصلاحية، المنطقة، الملاحظات).
11. `ConsentData`: الإقرارات الطبية (نوع الإقرار، وقت التوقيع، مرجع الملف).
12. `PhotoData`: صور الحالة الطبية (نوع الصورة، وقت الالتقاط، مرجع الملف).
13. `InvoiceData`: الفواتير (الإجمالي، الخصم، الضريبة، الصافي، الحالة).
14. `InvoiceItemData`: بنود الفاتورة (النوع، الوصف، الكمية، سعر الوحدة، الإجمالي).
15. `PaymentData`: الدفعات المسددة (المبلغ، طريقة الدفع، وقت الدفع، المرجع).
16. `PackageData`: باقات العروض (الاسم، عدد الجلسات، السعر، مدة الصلاحية).
17. `ClientPackageData`: باقات المريض المشتراة (اسم الباقة، الجلسات المتبقية، تاريخ الانتهاء).
18. `ProductData`: الأدوية والمستلزمات المخزنية (الاسم، الماركة، النوع، الوحدة، الكمية، التكلفة، السعر).
19. `SourceDocumentData`: أرشفة المستند الأصلي (اسم الملف، النوع، نص الـ OCR، وسجل الـ JSON).
* النموذج الرئيسي الشامل: **`LLMExtractionResult`** يضم قوائم لجميع الكيانات الـ 19 أعلاه.

## 6.3 المعالج اللغوي وهندسة البرومبتات وقواعد كتلة الدواء (`src/llm/llm_processor.py`)
يحتوي على البرومبت الأكثر تفصيلاً لمنع الهلوسة وفرض دقة الاستخراج:
* **قاعدة كتلة الدواء (Medication Block Rule):**
  * تبدأ كتلة الدواء بذكر اسم الدواء صراحة.
  * كل سطر يتبع اسم الدواء (مثل "قرص بعد الأكل مرتين يومياً لمدة أسبوع") ينتمي لنفس الدواء حتى يظهر اسم دواء جديد.
  * استخراج الجرعة والتكرار يتم فقط من الكتلة ذاتها، ويُمنع منعاً باتاً نقل جرعة دواء لآخر.
  * الحفاظ على اسم الدواء كما هو بحروفه ولغته دون ترجمة أو تعريب أو تطبيع.
* **خوارزميات تطبيع التواريخ والأرقام:**
  * `_normalize_numeric_values`: تحويل القيم الرقمية للنصوص إلى `float` أو `int`.
  * `_normalize_string_values`: تنظيف المسافات وتحويل النصوص الفارغة إلى `None`.
  * `_normalize_dates`: تحويل أي صيغة تاريخ واضحة إلى المعيار الدولي `YYYY-MM-DD`؛ وإذا كان التاريخ غير مكتمل أو غامضاً يتم إرجاعه كـ `None` لمنع التخمين.
  * تطبيع حقول الوقت والتاريخ المركبة إلى `YYYY-MM-DD HH:MM:SS`.

# الباب السابع: حواجز الأمان ومنع الهلوسة والتحقق (Validation & Guardrails)

## 7.1 حارس استخراج الروشتات وعزل الجداول (`src/validation/extraction_guard.py`)
ابتكار نوعي لحماية قاعدة البيانات من الهلوسة الناتجة عن نماذج الذكاء الاصطناعي:
* **فحص كلمات الروشتات:** يبحث عن كلمات مثل (`prescription`, `rx`, `دواء`, `ادوية`, `روشتة`, `علاج`, `مرات يوميا`, `قرص`, `كبسولة`, `قطرة`, `مرهم`).
* **عزل الجداول (Table Isolation):** إذا تيقن الحارس أن المستند روشتة طبية، يقوم فوراً وبشكل قسري بتصفير الجداول الـ 17 الأخرى (مثل المواعيد، الفواتير، العمليات، الخدمات) ويبقي فقط على جدول `medications`؛ لأن الروشتة لا يمكن أن تحتوي على فواتير أو إقرارات، وأي استخراج لها يعتبر هلوسة من النموذج.
* **تنظيف السجلات الفارغة (`_guard_empty_entities`):** حذف أي سجل كيان إذا كانت جميع حقوله فارغة أو تحتوي على `None`.

## 7.2 مدقق البيانات الميداني (`src/validation/validator.py`)
* يستدعي `LLMExtractionResult.model_validate(data)`.
* في حال النجاح يعيد: `{"valid": True, "data": normalized_data, "errors": []}`.
* في حال الفشل يعيد قائمة أخطاء تفصيلية تحدد الحقل المخالف ونوع الخطأ بدقة.

# الباب الثامن: طبقة قاعدة البيانات العلائقية والمعاملات الذرية (Database Layer)

## 8.1 إدارة الاتصال بـ SQL Server عبر pyodbc (`src/database/database.py`)
* سلسلة الاتصال المعتمدة:
  ```text
  DRIVER={ODBC Driver 18 for SQL Server};
  SERVER=localhost;
  DATABASE=ZaWolfDB;
  Trusted_Connection=yes;
  TrustServerCertificate=yes;
  ```
* توفر دوال التنفيذ والاستعلام واسترجاع المعرف التلقائي `OUTPUT INSERTED.id`.

## 8.2 المستودع الأساسي والعمليات العامة (`src/database/repository.py`)
* فئة `Repository(table_name)`:
  * تقوم بإنشاء استعلامات الإدخال البارامترية (Parameterized SQL) تلقائياً بناءً على مفاتيح القاموس لمنع ثغرات الحقن (SQL Injection).
  * تستخدم `OUTPUT INSERTED.id` لإرجاع المعرف الذي تم توليده فوراً لاستخدامه في ربط الجداول التابعة.
  * تدعم تمرير الـ `cursor` الخارجي للمشاركة في المعاملة الذرية الموحدة.

## 8.3 محلل العلاقات وتخريج المفاتيح الأجنبية (`src/database/relation_resolver.py`)
مسؤول عن تخريج المفاتيح الأجنبية والبحث عن السجلات الموجودة مسبقاً لمنع التكرار:
* `find_client(client, cursor)`: يبحث عن المريض بمطابقة: `first_name` و `last_name` ورقم الهاتف `mobile`.
* `find_staff(full_name, cursor)`: يبحث عن الطبيب أو الموظف باسمه الكامل.
* `find_location(name, cursor)`: يبحث عن الفرع.
* `find_service(name, cursor)`: يبحث عن الخدمة الطبية.
* `find_product(name, cursor)`: يبحث عن المنتج في المخزن.
* `find_package(name, cursor)`: يبحث عن الباقة العلاجية.

## 8.4 خريطة الحفظ المتكامل والتراجع التام (`src/database/mapper.py`)
الفئة الأكثر أهمية في طبقة البيانات؛ تنظم الحفظ في 19 جدولاً وفق ترتيب الأسبقية العلائقية:
1. الفروع (`locations`) ──► تُدرج أولاً.
2. الموظفون والأطباء (`staff`) ──► يُربط بـ `location_id`.
3. المرضى (`clients`) ──► تُجمع معرفاتهم في `client_ids`.
4. السجلات الطبية (`medical_history`, `vitals`, `lab_results`, `medications`) ──► تُربط بـ `client_id` (يُسمح للأدوية بدون مريض في الروشتات العامة).
5. الخدمات والباقات والمنتجات (`services`, `packages`, `products`).
6. المواعيد (`appointments`) ──► تُربط بـ `client_id`, `staff_id`, `location_id`, `service_id`.
7. سجلات العلاج (`treatment_records`) ──► تُربط بـ `appointment_id`, `product_id`.
8. الإقرارات (`consents`) والصور الطبية (`photos`) ──► تُربط بـ `client_id` و `treatment_id`.
9. الفواتير (`invoices`) ──► تُربط بـ `client_id` و `appointment_id`.
10. بنود الفواتير (`invoice_items`) والمدفوعات (`payments`) ──► تُربط بـ `invoice_id`.
11. باقات العميل (`client_packages`) ──► تُربط بـ `client_id` و `package_id`.
12. المستند المصدر (`source_documents`) ──► أرشفة الملف والنص وسجل الـ JSON.

### ضمان المعاملة الذرية والتراجع (Atomicity & Rollback):
تنفذ الدالة `save(data)` كافة الإدخالات على نفس الـ `cursor` في اتصال واحد؛ وفي حال حدوث أي خطأ في أي جدول:
```python
except Exception:
    connection.rollback()
    raise
```
يتم استدعاء `rollback()` فوراً لإلغاء المعاملة بالكامل ومسح كل السجلات التي أُدخلت، مما يضمن خلو قاعدة البيانات من أي سجلات تالفة أو يتيمة.

# الباب التاسع: المنسق العام للعمليات (Pipeline Orchestration)

## 9.1 فئة `ProcessingPipeline` في (`src/pipeline.py`)
تجمع كافة الطبقات السابقة وتدير مسار العمل الشامل عبر واجهة بسيطة:
* `__init__(ocr_engine="qwen")`: تهيئة المعالج وموجه الـ OCR والمحرك اللغوي والمدقق والمخزن.
* `process_file(file_path)`: مسار الفحص والتحليل والاستخراج دون حفظ؛ مفيد للمعاينات.
* `process_and_save_file(file_path)`: المسار الإنتاجي الكامل؛ يفحص، يوجه، يستخرج، يمرر للـ LLM، يطبق الحارس، يدقق عبر Pydantic، يضيف سجل المستند المصدر، ويحفظ في SQL Server ويعيد تقريراً بالمعرفات المسجلة.
* `_process_pdf_file`: التمييز والتوجيه بين الـ Digital والـ Scanned PDF.
* `_process_scanned_pdf`: تحويل الصفحات لصور، استخراج النصوص عبر موجه الـ OCR، وحساب متوسط نسبة الثقة.
* `_process_digital_pdf`: استخراج الدفعات وتقطيعها واستدعاء الـ LLM ودمج النتائج.
* `_process_image`: تحسين التباين ثم تمرير الصورة لموجه الـ OCR.
* `_process_word`: استخراج الفقرات والجداول.
* `_process_structured_file`: استخراج جداول الإكسيل والـ CSV وإعداد ملخص إحصائي لها.
